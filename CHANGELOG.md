# Changelog — meta-edgefirst-phytec

All notable changes to the `meta-edgefirst-phytec` Yocto layer are documented here.

## [Unreleased]

### Layer Changes

- Initial layer. The PHYTEC-specific content was migrated out of `meta-edgefirst`, which is vendor-neutral: RAUC is used only by the PHYTEC line (Torizon updates over SOTA/OSTree, Ezurio has its own mechanism), the device keyring is switched on the `update` override that only PHYTEC's `ampliphy-*-rauc` distros define, the bundle bbappends target `meta-ampliphy` recipes, and the published bundles live under `https://repo.edgefirst.ai/phytec/`.
- **RAUC bundles are signed by an EdgeFirst CA rather than PHYTEC's published development CA.** `recipes-core/rauc/rauc-conf.bbappend` installs `edgefirst-root.crt.pem` as the device keyring, and `recipes-images/bundles/edgefirst-rauc-signing.inc` (required by the `phytec-headless-bundle` and `phytec-artifacts-bundle` bbappends) selects the signing key, leaf and intermediate. `EDGEFIRST_CERT_PATH` points at the CA directory; `EDGEFIRST_SIGNING_CERT_PATH` defaults to it and can select different signing material, which is what allows a bundle to be signed with an outgoing key while shipping a new keyring. Both halves `bbfatal` when unset or incomplete, so a build cannot silently fall back to the dev CA, whose intermediate private key is published and whose root is valid to 2119. The keyring is switched on the `update` override, because `rauc-conf` is parsed in every build directory and an unconditional assignment makes `SRC_URI` unresolvable in non-RAUC ones. The chain is a root CA trusted by devices, one intermediate per BSP vendor shipped inside the bundle, and a signing leaf; a leaf needs `extendedKeyUsage = codeSigning, emailProtection`, since RAUC's `CMS_verify` applies the S/MIME signing purpose and rejects an EKU without `emailProtection`.
- `scripts/make-edgefirst-ca.sh` generates the root, a vendor intermediate and a signing leaf (RSA-4096). `scripts/publish-rauc-bundle.sh` uploads a bundle, the root certificate and a `latest.json` pointer to `s3://edgefirst-repo/<vendor>/<machine>/` behind CloudFront, served publicly from `https://repo.edgefirst.ai` so streamed installs need no signed URLs.
- **The DHCPv4 client identifier is pinned to the MAC address.** `recipes-core/systemd/systemd-conf_%.bbappend` installs a `ClientIdentifier=mac` drop-in into every `.network` unit that enables DHCP. systemd-networkd otherwise derives the identifier from the machine ID, and images ship `/etc/machine-id` empty so that the first boot generates one; on a RAUC A/B system every slot activation is a first boot, so the DHCP lease changed on each update even though the MAC did not. Installed from a `do_install[postfuncs]` rather than a `do_install:append` because the units it iterates over are installed by other layers' append fragments, whose order relative to this one is undefined. The drop-in source path falls back to `WORKDIR` where `UNPACKDIR` is undefined.
- **The neutron kernel driver negotiates its mailbox reset value.** `recipes-kernel/linux/linux-phytec-imx_%.bbappend` backports the handshake from the 6.18.37 BSP so the driver works with eIQ Neutron SDK 3.2.x firmware, which `meta-edgefirst` now ships at 3.2.3 for YOLO11/26 accuracy. 3.2.x replies `0xA1` to a reset where PHYTEC's 6.18.20-based driver expects `0x0` and spins until its retry budget runs out, leaving the NPU unusable. NXP's fix makes the expected reply a runtime value that falls back to `0x0`, so one kernel drives either generation of runtime and 3.1.x boards keep working; it also writes `POLL` ahead of the arguments in the send and reset paths, closing a race where the firmware woke on the argument writes and read a stale request. Scoped to `mx95-nxp-bsp` because `drivers/staging/neutron` exists only on the SoCs carrying the NPU, and the i.MX 8M Plus kernel built from the same recipe name has no such directory. Drop the append once PHYTEC rebases onto a 6.18.37 or later kernel, which already carries the change.
- **The image payload is installed from the layer, not from `local.conf`.** `packagegroup-edgefirst-phytec` composes the capability packagegroups from `meta-edgefirst` and adds what is a PHYTEC fact: meta-ampliphy's own `packagegroup-camera`, and `phycam-imx95-dewarp-configs` for the phyCAM modules this board family accepts. `recipes-images/images/phytec-headless-image.bbappend` installs it, so a build is reproducible from a manifest sync with nothing in `local.conf`. An `IMAGE_INSTALL:append` in a conf file is a datastore operation applied after every image recipe's own assignment, so it reaches images it was never meant for; inside a recipe bbappend the append is scoped to that recipe by definition.
- Which capabilities a machine gets is decided here rather than inside the generic packagegroups, which describe only what a capability is. The i.MX 95 line takes the camera stack; the i.MX 8M Plus line ships no camera stack. Both take `packagegroup-edgefirst-codec` for hardware video.
- **The image ships no GStreamer.** EdgeFirst's components reach the camera through V4L2 and libcamera and the video encoder and decoder through the V4L2 memory-to-memory API, so GStreamer adds nothing the payload uses and anyone who wants it can enable it separately. Dropping it removes 103 packages on i.MX 8M Plus and 366 on i.MX 95 — the larger figure because meta-ampliphy's `packagegroup-gstreamer` pulled all of `gstreamer1.0-plugins-bad` and `libav` — and takes the i.MX 95 bundle from 369 MB to 329 MB. The codec userspace is unaffected: `imx-vpu-hantro` with its arbitration daemon on i.MX 8M Plus, `firmware-imx-vpu-wave` on i.MX 95. A dozen GStreamer core packages remain on i.MX 95 because PipeWire's `gstreamer1.0-pipewire` plugin links them, which is a distro dependency rather than part of this payload.
- `recipes-images/packagegroups/packagegroup-edgefirst-gstreamer.bbappend` adds meta-ampliphy's `packagegroup-gstreamer` on i.MX 95, so that enabling `packagegroup-edgefirst-gstreamer` on a PHYTEC board brings a working stack. `meta-edgefirst` supplies the plugin set on i.MX 8M Plus from meta-freescale-distro, but on i.MX 95 the platform GStreamer is a vendor fact and belongs here. The switch stays i.MX 95 only until `edgefirst-gstreamer` 0.4.0 builds against `edgefirst-hal` 0.28.3 on the walnascar pin, which it currently does not, the recipe carrying no `LAYERSERIES` guard to select an older revision.
- Verified by diffing the resolved rootfs manifest on both `imx95-phyflex-libra-rdk-2` and `imx8mp-phyflex-libra-rdk-2`, which is the only way to check a packagegroup refactor: `IMAGE_INSTALL` holds one group name instead of the package list, so it cannot be compared textually. Moving the payload out of `local.conf` was payload-neutral apart from the marker packages; removing GStreamer accounts for every other difference.
